# 镜像部署评估

这是 v1.0.0 测试镜像的操作入口。没有对应开源仓库的成功发布作业时，请使用[源码试用](../README.md#在本机试用)，不要猜测镜像地址。

Linux amd64/arm64 主机需要 Docker 和 Compose 2.24+。从开源源码包取得 `deploy`、`compose.deploy.yaml` 和示例文件，保留它们的相对位置，不需要在服务器安装 Node.js。

```sh
./deploy init
./deploy up
./deploy seed --demo
./deploy status
```

初始化依次选择：

1. 角色 `all`，即 Web、CMS、PostgreSQL、MinIO；首版试用选环境 `demo`。
2. Release 填 **v1.0.0**；GHCR owner 填实际开源仓库发布镜像的账号，不能保留占位值。
3. 应用与数据绑定保持 `127.0.0.1`，默认端口 3000/3001/5432/9000/9001。不要和源码试用同时占用这些端口。
4. 数据目录选 Docker 管理卷或自己专用目录；不要复用自用门户数据。
5. 公共镜像可以匿名拉取。若镜像确实为私有，才使用有 `read:packages` 权限的凭据登录；镜像还没发布导致的拉取失败不能靠扩大令牌权限解决。

`up` 会拉取并核对版本、架构、组件与 digest，启动数据服务，执行显式迁移，再启动应用。只有初次建立虚构数据时才执行 `seed --demo`；该动作会重设演示账号和首页。登录资料保存在本机 `.ascnucc/deploy.env`，只在本地查看并妥善保管。

日常使用 `./deploy stop`、`./deploy start`、`./deploy restart`；这些命令不删除数据卷。`./deploy logs cms` 和 `./deploy doctor` 用于诊断。已部署的镜像 digest 记录在 `.ascnucc/state.env`，不要手工改状态来跳过检查。

更新前备份数据库、对象存储和配置，再执行 `./deploy update v1.0.0`（未来更新时改成实际目标版本）。首版没有稳定频道；不要省略版本或选择 `latest`。迁移成功但新应用失败时，工具不会擅自把旧代码接回新数据库，应停止并评估修复或完整恢复。

工具支持分角色部署，但涉及外部数据库、S3、网络和 TLS，需要自行验证。它不提供生产 owner 初始化/恢复、完整灾备或长期运维保证；详见[运维手册](README.md#容器镜像与正式环境)。
